# Product Requirements Document: GQAI Study

- 버전: 1.0
- 작성일: 2026-09-03
- 상태: MVP v1 구현 기준선
- 제품 등급: Level 3 Full Project
- 소유자: 서비스 운영 강사

## 1. 제품 요약

GQAI Study는 강사가 직접 작성한 실습 모듈을 학생 또는 그룹에 배정하고, 학생별 학습 상태·제출물·피드백·재제출 이력을 관리하는 초대 전용 프라이빗 학습관리 서비스다.

기존 Notion 문서는 과제 내용을 전달하는 데는 적합하지만 학생별 배정과 실행 결과를 상태로 관리하기 어렵다. GQAI Study는 `재사용 가능한 콘텐츠`와 `학생별 실행 기록`을 분리해 이 문제를 해결한다.

## 2. 제품 비전

강사는 여러 도구를 오가며 학생별 상황을 기억하지 않아도 되고, 학생은 로그인하자마자 지금 해야 할 학습과 받은 피드백을 이해할 수 있어야 한다.

장기적으로는 일정, 알림, 결제, AI 피드백을 연결할 수 있지만 MVP는 사람 강사와 학생 사이의 과제 실행 루프를 정확하게 만드는 데 집중한다.

## 3. 문제 정의

### 3.1 강사의 문제

- 과제 내용을 매번 복사해 학생에게 전달해야 한다.
- 여러 학생에게 같은 과제를 보내도 진행 상태는 따로 추적해야 한다.
- 제출물이 메신저, 이메일, 클라우드 링크 등에 흩어진다.
- 누가 미제출인지, 누가 피드백을 기다리는지 한눈에 보기 어렵다.
- 과제 원본을 수정하면 과거 학생에게 무엇을 안내했는지 확인하기 어렵다.
- 그룹 구성 변경과 과거 학습 이력이 섞일 수 있다.

### 3.2 학생의 문제

- 현재 해야 할 과제와 과거 과제를 구분하기 어렵다.
- 과제 설명, 참고자료, 제출 위치가 서로 다른 도구에 있다.
- 수강 여부를 스스로 기록할 일관된 방법이 없다.
- 피드백 이후 무엇을 수정해야 하는지와 완료 여부가 불명확하다.

## 4. 목표와 비목표

### 4.1 MVP 목표

- 강사가 모듈을 한 번 작성하고 재사용할 수 있다.
- 개인·복수 학생·그룹 배정을 한 흐름에서 처리할 수 있다.
- 그룹 배정이 학생별 독립 기록으로 변환된다.
- 학생이 모든 기본 제출 유형을 사용할 수 있다.
- 피드백, 재제출, 최종 완료 이력이 보존된다.
- 역할과 소유권에 따른 데이터 격리가 검증된다.

### 4.2 MVP 비목표

- 결제와 수강권 운영
- 실시간 수업, 채팅, 예약
- AI 자동 평가와 자동 피드백
- 공동 그룹 제출
- 학생 자유 가입과 소셜 로그인
- 다중 강사 조직과 외부 강사 초대
- 성적, 순위, 수료증
- Notion 동기화

## 5. 사용자와 역할

### 5.1 관리자/강사

특성:

- 서비스를 직접 운영하는 단일 관리자
- 모듈 콘텐츠의 작성자이자 피드백 제공자
- 학생 계정과 그룹의 유일한 관리자

주요 성공 상태:

- 모듈을 빠르게 재사용한다.
- 제출과 피드백 대기 건을 놓치지 않는다.
- 학생별 전체 이력을 한 화면에서 확인한다.

### 5.2 학습자

특성:

- 강사에게 계정을 받아 접속한다.
- 개인 과제 또는 그룹 일괄 배정으로 카드를 받는다.
- 학습과 제출 결과는 언제나 개인 기록으로 남는다.

주요 성공 상태:

- 지금 할 일을 이해한다.
- 원하는 형식으로 결과물을 제출한다.
- 피드백에 따라 수정하고 완료 여부를 확인한다.

| 과제 상태 | 제출과 피드백이 진행된 단계                   |
| 제출 차수 | 최초 제출 및 재제출의 순서                    |
| 최종 완료 | 강사가 더 이상 수정이 필요 없다고 확정한 상태 |

## 7. 제품 원칙

1. 학생의 첫 화면은 콘텐츠 탐색보다 `지금 할 일`을 우선한다.
2. 그룹 작업은 강사의 반복만 줄이고 학생 기록을 합치지 않는다.
3. 과거 기록은 최신 데이터로 덮어쓰지 않는다.
4. 상태는 자동 추측보다 명시적 사용자 행동으로 변경한다.
5. 관리자 권한은 UI 표시가 아니라 서버와 데이터베이스에서 검증한다.
6. 파일은 공개 편의보다 학생 개인정보 보호를 우선한다.
7. 미래 기능은 확장 경계를 마련하되 MVP 복잡도를 늘리지 않는다.

## 9. 상태 모델

### 9.1 모듈 상태

```text
draft → published → archived
  ↑         │
  └─ 새 초안/버전 생성
```

- 발행된 버전 자체는 수정하지 않는다.
- 보관은 새 배정만 막고 과거 열람은 유지한다.

### 9.2 배정 카드 상태

수강 상태:

```text
not_started → in_progress → course_completed
                     ↘ 필요하면 in_progress로 되돌림
```

과제 상태:

```text
not_submitted
  → submitted
  → feedback_given
  → revision_requested
  → resubmitted
  → completed
```

예외 상태:

- `cancelled`: 학생 활동 전 관리자 취소
- `stopped`: 활동 후 관리자가 중단

수강 상태와 과제 상태는 서로 독립적이다. 제출했다고 수강 완료로 자동 처리하지 않는다.

### 9.3 제출 상태

```text
draft → submitted → superseded
```

- 최신 재제출이 생기면 이전 제출을 `superseded`로 표시할 수 있지만 읽기 가능해야 한다.

## 12. 비기능 요구사항

### 12.1 보안

- 모든 핵심 테이블에 RLS를 활성화한다.
- 역할 검사는 데이터 접근 계층과 각 서버 작업에서 수행한다.
- 관리자 Auth API와 service role은 서버에서만 사용한다.
- 파일 버킷은 비공개다.
- 파일 접근 URL은 짧은 시간만 유효해야 한다.
- 사용자 입력은 스키마 검증 후 처리한다.
- 외부 URL은 `http/https`만 허용하고 화면 출력 시 안전하게 처리한다.
- 리치 콘텐츠는 저장과 렌더링 양쪽에서 스크립트 삽입을 차단한다.
- 로그에 비밀번호, 토큰, 서명 URL, 제출물 본문을 남기지 않는다.

### 12.2 개인정보

- MVP에서 필요한 최소 정보는 로그인 아이디와 표시 이름이다.
- 이메일과 전화번호는 수집하지 않는다.
- 비활성화 후 보존 정책을 운영 전에 고지한다.
- 운영 배포 전 개인정보 처리방침 위치를 마련한다.

### 12.3 성능

- 일반적인 보호 페이지의 핵심 콘텐츠는 정상 네트워크에서 2.5초 이내 표시를 목표로 한다.
- 목록은 처음부터 전체를 가져오지 않고 페이지네이션한다.
- 이미지에는 크기 정보와 지연 로딩을 적용한다.
- 파일 업로드 중 페이지가 멈추지 않고 진행 상태를 표시한다.
- 관리자 대시보드 집계는 한 번의 화면 진입에서 과도한 개별 쿼리를 만들지 않는다.

### 12.4 안정성

- 그룹 배정은 트랜잭션으로 처리한다.
- 중복 요청을 받아도 같은 학생에게 동일 배정이 의도치 않게 두 번 생성되지 않도록 요청 키 또는 제약을 둔다.
- 파일 업로드와 DB 기록이 어긋나면 고아 파일 정리 경로를 둔다.
- 상태 전이는 허용된 이전 상태에서만 가능하다.

### 12.5 접근성

- 모든 폼 입력에는 연결된 레이블이 있다.
- 키보드만으로 로그인, 모듈 열람, 제출, 피드백이 가능하다.
- 색상만으로 상태를 구분하지 않는다.
- 포커스 표시를 제거하지 않는다.
- 이미지 블록은 대체 텍스트를 입력할 수 있다.
- 오류는 입력 필드 가까이와 요약 영역에 표시한다.

### 12.6 반응형

- 최소 360px 폭에서 핵심 흐름을 완료할 수 있다.
- 표는 모바일에서 카드 또는 가로 스크롤로 안전하게 전환한다.
- 제출 버튼과 상태 변경 버튼은 모바일에서 화면 밖으로 밀리지 않는다.

## 15. 성공 지표

### 15.1 제품 성공

- 강사가 새 모듈을 발행하고 그룹에 배정할 수 있다.
- 그룹 구성원 전원에게 개별 카드가 빠짐없이 생성된다.
- 학생이 모바일에서 로그인부터 제출까지 완료할 수 있다.
- 관리자가 제출을 열어 피드백하고 완료 처리할 수 있다.
- 한 카드의 전체 이력이 시간순으로 보존된다.

### 15.2 운영 성공

- 권한 누출 테스트 0건
- 그룹 배정 부분 실패 0건
- 고아 파일 생성 0건
- 프로덕션 핵심 경로 5xx 오류 0건
- 서비스 역할 키의 클라이언트 노출 0건

### 15.3 실패 판단

다음 중 하나라도 발생하면 MVP 출시를 보류한다.

- 학생이 다른 학생의 카드 또는 파일을 열 수 있다.
- 원본 모듈 수정이 기존 배정 내용을 변경한다.
- 그룹 배정 일부만 저장되고 나머지가 실패한다.
- 재제출이 과거 제출을 덮어쓴다.
- 관리자가 사용자의 기존 비밀번호 원문을 볼 수 있다.
- 프로덕션에서 미로그인 사용자가 보호 데이터를 읽을 수 있다.

## 16. 통합 수용 기준

### 인증

- [ ] 자가 회원가입 URL이 존재하지 않거나 사용 불가다.
- [ ] 관리자가 만든 학생 계정으로만 로그인할 수 있다.
- [ ] 최초 로그인 후 비밀번호 변경 전에는 학습 화면에 들어갈 수 없다.
- [ ] 비활성 학생의 기존 세션과 새 로그인이 차단된다.
- [ ] 로그아웃 후 뒤로 가기 또는 직접 URL 입력으로 보호 데이터를 볼 수 없다.

### 모듈

- [ ] 요구된 모든 콘텐츠 블록이 저장 후 동일하게 렌더링된다.
- [ ] 발행된 버전은 불변이다.
- [ ] 새 버전 발행 전 기존 배정은 이전 버전을 계속 사용한다.
- [ ] 보관된 모듈은 새 배정 선택 목록에 나타나지 않는다.

### 그룹과 배정

- [ ] 학생을 여러 그룹에 넣을 수 있다.
- [ ] 그룹 배정은 현재 활성 구성원 수와 같은 수의 카드를 만든다.
- [ ] 같은 학생이 중복 대상이어도 의도하지 않은 중복 카드가 생기지 않는다.
- [ ] 배정 실패 시 부분 데이터가 남지 않는다.
- [ ] 그룹 멤버 변경이 과거 배정을 바꾸지 않는다.

### 학습과 제출

- [ ] 첫 열람, 학습 시작, 수강 완료 시각이 구분된다.
- [ ] 수강 완료와 과제 완료가 독립적으로 표시된다.
- [ ] 네 가지 제출 형식이 한 제출 안에서 함께 동작한다.
- [ ] 업로드 실패 파일만 다시 시도할 수 있다.
- [ ] 재제출 후 모든 과거 차수를 조회할 수 있다.

### 피드백

- [ ] 관리자가 특정 제출 차수에 피드백을 남긴다.
- [ ] 재제출 요청이 학생의 할 일 목록에 나타난다.
- [ ] 학생이 피드백을 읽은 시각이 기록된다.
- [ ] 학생 답변과 관리자 피드백의 작성자가 구분된다.
- [ ] 최종 완료 후 새 제출이 차단된다.

### 권한과 파일

- [ ] 학생 A가 학생 B의 식별자를 URL에 넣어도 404 또는 권한 없음 결과를 받는다.
- [ ] 학생 제출 파일은 공개 URL로 열리지 않는다.
- [ ] 관리자만 전체 학생의 파일을 열 수 있다.
- [ ] 만료된 파일 URL은 다시 발급받기 전 열리지 않는다.
- [ ] service role 키가 브라우저 네트워크·번들·로그에 없다.
