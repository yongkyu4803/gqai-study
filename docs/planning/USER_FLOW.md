# User Flow: GQAI Study

- 작성일: 2026-09-03
- 대상: 관리자/강사, 강사가 등록한 학생
- 원칙: 모든 보호 경로는 로그인·역할·데이터 소유권을 검사한다.

## 1. 전체 서비스 진입

### 미로그인 사용자

1. 사용자가 `/` 또는 보호 URL로 접속한다.
2. `/`는 서비스 소개와 로그인 버튼만 제공한다.
3. 보호 URL은 `/login?next={원래경로}`로 이동한다.
4. 사용자가 아이디와 비밀번호를 입력한다.
5. 인증 후 최초 비밀번호 변경 여부를 확인한다.
6. 변경이 필요하면 `/change-password`로 이동한다.
7. 변경이 끝나면 `next` 또는 역할별 대시보드로 이동한다.

### 역할별 기본 경로

| 역할 | 기본 경로 | 첫 화면의 핵심 행동 |
| --- | --- | --- |
| 관리자 | `/admin` | 제출 대기 확인 또는 새 카드 배정 |
| 학생 | `/learn` | 가장 우선인 배정 카드 열기 |

## 3. 관리자 계정 및 학생 발급 흐름

### 3.1 학생 계정 생성

1. 관리자가 `/admin/students`에서 `학생 추가`를 누른다.
2. 표시 이름, 로그인 아이디, 임시 비밀번호, 초기 그룹을 입력한다.
3. 클라이언트에서 형식만 사전 검사한다.
4. 서버가 관리자 세션과 역할을 다시 검사한다.
5. 서버가 아이디 중복, 비밀번호 정책, 그룹 유효성을 검사한다.
6. Auth 계정과 `profiles` 행을 생성한다.
7. 선택한 그룹 멤버십을 생성한다.
8. 성공 화면에 아이디와 이번에 입력한 임시 비밀번호를 한 번 표시한다.
9. 관리자가 안전한 방법으로 학생에게 전달한다.
10. 화면을 떠난 뒤에는 비밀번호를 다시 표시하지 않는다.

성공 상태:

- 생성된 학생 이름과 아이디
- 소속 그룹
- `임시 비밀번호는 다시 확인할 수 없음` 경고
- 학생 상세 또는 추가 생성으로 이동

오류 상태:

- 중복 아이디: 아이디 입력란을 유지하고 대안 안내
- Auth 생성 실패: 프로필이나 그룹만 남지 않도록 전체 취소
- 그룹 저장 실패: 생성 작업 전체를 되돌리거나 명확히 복구

### 3.2 비밀번호 재설정

1. 관리자가 학생 상세에서 `비밀번호 재설정`을 선택한다.
2. 대상 이름과 아이디를 확인한다.
3. 새 임시 비밀번호를 입력 또는 생성한다.
4. 서버가 관리자 권한을 확인하고 Auth 비밀번호를 갱신한다.
5. `must_change_password`를 다시 켠다.
6. 기존 세션 무효화 가능 여부를 적용하고 감사 로그를 남긴다.

### 3.3 학생 비활성화

1. 관리자가 학생 상세에서 비활성화를 누른다.
2. 기존 학습 기록이 삭제되지 않는다는 설명을 본다.
3. 확인 후 계정을 비활성화한다.
4. 새 로그인과 보호 작업을 차단한다.
5. 관리자 화면에는 `비활성` 배지가 붙고 이력은 유지된다.

## 4. 로그인 흐름

### 입력

- 로그인 아이디
- 비밀번호
- 원래 접근 경로 `next`는 숨은 상태로 보존

### 성공

- 최초 로그인: `/change-password`
- 일반 관리자: `next`가 관리자 허용 경로면 해당 경로, 아니면 `/admin`
- 일반 학생: `next`가 본인 허용 경로면 해당 경로, 아니면 `/learn`

### 오류

| 상황 | 표시 문구 방향 | 다음 행동 |
| --- | --- | --- |
| 빈 입력 | 필수 항목 안내 | 입력 |
| 잘못된 자격 증명 | 아이디 또는 비밀번호 확인 | 재시도 |
| 비활성 계정 | 강사에게 문의 | 로그인 |
| 과도한 실패 | 잠시 후 다시 시도 | 대기 |
| 서버 오류 | 입력값 중 비밀번호만 비움 | 재시도 |

개방형 리다이렉트를 막기 위해 `next`는 서비스 내부 허용 경로만 사용한다.

## 5. 모듈 작성과 발행 흐름

### 5.1 새 모듈 작성

1. 관리자가 `/admin/modules`에서 `새 모듈`을 선택한다.
2. 기본 정보와 콘텐츠 블록을 작성한다.
3. 이미지·PDF·일반 자료를 업로드한다.
4. 자동 저장 또는 명시적 저장으로 초안을 보존한다.
5. 저장 상태가 `저장 중 → 저장됨`으로 바뀐다.
6. 미리보기에서 학생이 볼 형태를 확인한다.

기본 정보:

- 제목
- 한 줄 요약
- 카테고리
- 난이도
- 예상 시간
- 태그
- 학습 목표
- 준비물
- 제출 요구사항
- 완료 기준

지원 블록:

- 문단, 제목 2~4
- 글머리/번호 목록
- 체크리스트
- 인용문, 구분선
- 코드 블록
- 링크 카드
- 이미지
- PDF
- 일반 첨부파일

### 5.2 발행

1. 관리자가 `발행`을 누른다.
2. 시스템이 제목, 본문, 제출 요구사항과 깨진 업로드를 검사한다.
3. 현재 초안의 고정 스냅샷과 버전 번호를 보여준다.
4. 관리자가 확인한다.
5. 변경 불가능한 `module_version`을 생성한다.
6. 모듈을 `사용 가능` 상태로 전환한다.
7. `지금 배정하기` 또는 모듈 목록으로 이동한다.

발행 실패 시 초안을 그대로 유지한다.

### 5.3 발행 후 수정

1. 관리자가 사용 가능한 모듈에서 `새 버전 편집`을 누른다.
2. 최신 발행 내용을 새 초안으로 복사한다.
3. 수정 후 다시 발행하면 버전 번호가 증가한다.
4. 기존 배정 카드는 이전 버전을 계속 사용한다.

## 6. 그룹 관리 흐름

### 그룹 생성

1. 관리자가 그룹 이름과 설명을 입력한다.
2. 활성 학생을 검색해 복수 선택한다.
3. 저장 후 그룹 상세에서 구성원을 확인한다.

### 구성원 변경

- 학생 추가: 이후 그룹 배정부터 포함
- 학생 제거: 이후 그룹 배정에서 제외
- 과거 배정: 어느 경우에도 변경하지 않음

그룹 상세에는 다음을 표시한다.

- 활성/보관 상태
- 현재 구성원 수와 목록
- 과거 그룹 배정 배치
- 배정 당시 대상 수
- 현재 구성원과 과거 대상이 다를 수 있다는 안내

## 7. 개인·복수·그룹 배정 흐름

### 7.1 배정 준비

1. 관리자가 `/admin/assign`에 들어간다.
2. 사용 가능한 모듈과 발행 버전을 선택한다.
3. 대상 방식을 선택한다.
   - 학생 직접 선택: 한 명 또는 여러 명
   - 그룹 선택: 그룹 한 개
4. 공통 안내문을 작성한다.
5. 미래 확장용 마감일 위치는 표시하되 MVP에서는 비활성으로 둔다.

### 7.2 배정 검토

검토 화면에 다음을 표시한다.

- 모듈 제목과 버전
- 대상 방식과 대상 이름
- 실제 생성될 학생별 카드 수
- 비활성 학생 제외 수
- 동일 버전의 열린 카드 중복 경고
- 그룹 배정은 현재 구성원에게만 적용된다는 설명
- 공통 안내문

### 7.3 배정 실행

1. 관리자가 최종 배정을 확인한다.
2. 클라이언트는 중복 클릭을 막는다.
3. 서버가 관리자 권한, 모듈 버전, 대상 상태를 다시 검사한다.
4. 하나의 배정 배치를 만든다.
5. 대상 학생마다 개별 배정 카드를 만든다.
6. 모두 성공하면 한 번에 커밋한다.
7. 결과 화면에서 생성된 카드 수와 학생 목록을 보여준다.

일부 학생만 저장되는 상태는 허용하지 않는다.

## 8. 학생 학습 흐름

### 8.1 첫 화면

`/learn`의 우선순위:

1. 재제출 요청
2. 새 피드백
3. 아직 시작하지 않은 카드
4. 학습 중 카드
5. 수강 완료했지만 최종 완료되지 않은 카드

완료 카드는 별도 탭 또는 `/history`에 둔다.

### 8.2 카드 상세

1. 학생이 카드를 연다.
2. 시스템이 학생 소유권을 확인한다.
3. 최초 열람이면 `first_opened_at`을 기록한다.
4. 모듈 콘텐츠와 개인 안내문을 표시한다.
5. 학생이 `학습 시작`을 누른다.
6. 학생이 각 자료와 체크리스트를 확인한다.
7. 학습 후 `수강 완료`를 기록한다.
8. 과제 제출이 필요하면 제출 화면으로 이동한다.

수강 완료를 취소할 수 있지만 변경 이력은 활동 로그에 남긴다.

### 8.3 학생 메모

- 메모는 강사 피드백이 아니라 학생 개인 메모다.
- 자동 저장 실패 시 입력을 유지하고 재시도한다.
- 관리자에게 공개할지 여부는 MVP에서 별도 옵션으로 만들지 않고 학생 본인 전용으로 둔다.

## 9. 제출 흐름

### 9.1 제출 작성

1. 학생이 카드에서 `결과물 제출`을 누른다.
2. 기존 미제출 초안이 있으면 복원한다.
3. 필요한 제출 항목 안내를 보여준다.
4. 학생이 항목을 원하는 순서로 추가한다.
   - 텍스트
   - 웹 링크
   - 이미지
   - 파일
5. 각 항목을 미리 확인한다.
6. 파일은 업로드 진행률과 실패 여부를 개별 표시한다.
7. 초안 저장 또는 제출을 선택한다.

### 9.2 제출 확인

제출 직전에 다음을 검증한다.

- 유효한 항목이 최소 1개인지
- 링크 형식이 올바른지
- 모든 파일 업로드가 끝났는지
- 제한 크기와 파일 형식을 통과했는지
- 카드가 제출 가능한 상태인지

확인 후:

- 제출 차수와 시간을 고정
- 과제 상태를 `submitted` 또는 `resubmitted`로 변경
- 관리자 검토 대기함에 표시
- 읽기 전용 제출 요약으로 이동

### 9.3 재제출

1. 학생이 재제출 요청을 확인한다.
2. 요청 대상 제출 차수와 수정 지시를 본다.
3. 이전 제출을 복사해 새 초안으로 시작하거나 빈 초안을 선택한다.
4. 새 차수로 제출한다.
5. 이전 제출과 피드백은 그대로 유지한다.

## 10. 관리자 피드백 흐름

1. 관리자가 `/admin/reviews`에 들어간다.
2. 오래된 제출, 학생, 그룹, 모듈로 필터링한다.
3. 제출 한 건을 연다.
4. 카드 내용, 학생 안내문, 수강 상태, 모든 제출 차수를 확인한다.
5. 최신 제출을 선택해 피드백을 작성한다.
6. 첨부파일이 있으면 비공개로 업로드한다.
7. 처리 결과를 선택한다.
   - 일반 피드백
   - 재제출 요청
   - 최종 완료
8. 저장 후 해당 카드의 상태와 검토 대기 목록이 갱신된다.

재제출 요청에는 구체적인 수정 지시가 필수다. 최종 완료는 확인 대화상자를 거친다.

## 11. 피드백 확인과 답변 흐름

1. 학생 대시보드에 `새 피드백` 배지가 나타난다.
2. 학생이 피드백 화면을 연다.
3. 시스템이 첫 읽음 시각을 기록한다.
4. 제출 차수별 피드백을 시간순으로 보여준다.
5. 학생은 텍스트 답변 또는 첨부파일을 남길 수 있다.
6. 재제출 요청이면 `수정해서 재제출` 행동을 강조한다.
7. 최종 완료면 모든 이력을 읽기 전용으로 보여준다.

## 12. 화면 상태 기준

| 상태 | 관리자 화면 | 학생 화면 |
| --- | --- | --- |
| 로딩 | 스켈레톤과 작업명 | 카드 스켈레톤 |
| 빈 목록 | 다음 생성 행동 제공 | 배정된 학습이 없다는 안내 |
| 저장 중 | 버튼 중복 실행 차단 | 초안 저장 상태 표시 |
| 성공 | 결과 수와 이동 경로 | 다음 행동 또는 내 학습 복귀 |
| 입력 오류 | 필드 가까이 구체적 안내 | 작성 내용 유지 |
| 서버 오류 | 작업이 적용되지 않았는지 명시 | 재시도와 안전한 복귀 |
| 권한 없음 | 관리자 대시보드로 복귀 | 내 학습으로 복귀 |
| 없는 자원 | 삭제를 추측하지 않는 404 | 카드 목록 복귀 |
| 세션 만료 | 로그인 후 원래 화면 복귀 | 로그인 후 초안 복원 시도 |

## 13. 주요 빈 상태 문구의 방향

- 관리자 모듈 없음: `첫 실습 모듈을 만들어 보세요.`
- 학생 없음: `학생 계정을 먼저 추가하면 과제를 배정할 수 있습니다.`
- 그룹 없음: `반복해서 함께 배정할 학생을 그룹으로 묶어 보세요.`
- 검토 대기 없음: `현재 확인할 제출물이 없습니다.`
- 학생 배정 없음: `아직 배정된 학습이 없습니다. 강사가 과제를 배정하면 여기에 표시됩니다.`
- 학생 피드백 없음: `아직 도착한 피드백이 없습니다.`
- 완료 기록 없음: `완료된 학습이 아직 없습니다.`

## 14. 권한·오류 예외 흐름

### 다른 학생 카드 URL 접근

1. 학생 A가 학생 B의 배정 URL을 요청한다.
2. 서버와 RLS가 소유권을 확인한다.
3. 존재 여부를 과도하게 노출하지 않고 404 또는 접근 불가를 반환한다.
4. 학생 A의 `/learn`으로 돌아갈 링크를 제공한다.

### 파일 URL 공유

1. 학생이 짧은 만료의 서명 URL을 복사한다.
2. URL은 만료 후 사용할 수 없다.
3. 새 URL 발급 요청에는 다시 카드 소유권을 확인한다.

### 그룹 배정 중 구성원 변경

1. 배정 검토 후 실행 전에 그룹이 변경될 수 있다.
2. 서버는 실행 시점의 구성원을 다시 읽는다.
3. 검토 화면과 인원이 달라지면 실행을 중단하고 재확인을 요구한다.

### 업로드 후 제출 실패

1. 파일 업로드는 끝났지만 제출 DB 작업이 실패한다.
2. 초안에 파일 참조를 유지해 재시도한다.
3. 참조되지 않은 파일은 만료 작업에서 고아 파일로 정리한다.

## 16. 사용자 흐름 검증 체크리스트

- [ ] 미로그인 상태에서 모든 보호 경로가 로그인으로 이동한다.
- [ ] 로그인 후 원래 허용 경로로 복귀한다.
- [ ] 최초 비밀번호 변경을 우회할 수 없다.
- [ ] 관리자 첫 화면에서 검토 대기까지 한 번에 이동한다.
- [ ] 새 모듈 작성부터 그룹 배정까지 길을 잃지 않는다.
- [ ] 그룹 인원과 생성 카드 수가 일치한다.
- [ ] 학생 첫 화면에서 가장 시급한 행동이 먼저 보인다.
- [ ] 학생이 모바일에서 네 가지 제출 유형을 사용할 수 있다.
- [ ] 재제출이 이전 제출을 덮어쓰지 않는다.
- [ ] 최종 완료 후 이력이 읽기 전용으로 남는다.
- [ ] 오류 후 입력 내용이 가능한 한 보존된다.
- [ ] 미래 기능이 아직 작동한다고 오해되지 않는다.
